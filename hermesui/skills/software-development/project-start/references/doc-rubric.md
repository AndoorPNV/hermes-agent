# Что считается заполненным документом

Планка качества для каждого файла, который создаёт `scaffold.py`. Проверять по ней,
а не по «документ не пустой». Общий принцип: **факт или маркер, ничего третьего.**

## 00-INDEX.md

- 3–6 проверяемых фактов с источником-командой (версия, размер, число эндпоинтов).
- Таблица состояния честная: если документация черновик — так и написано.
- Все относительные ссылки разрешаются (файл существует).

Плохо: «Подробная документация по всем аспектам проекта.»

## 01-SPECIFICATION.md

| Раздел | Обяз. содержание | Признак халтуры |
|---|---|---|
| Контекст | проблема, у кого, что сейчас | «в современном мире» |
| Продукт | одно предложение + 2–4 свойства | список фич |
| Цели | цель + **проверяемый** признак | «улучшить UX» |
| Не-цели | что не делаем и почему | пусто |
| FR | требование + **«Приёмка:»** | требование без приёмки |
| NFR | число/порог | «быстро», «надёжно» |
| Ограничения | техническое «нельзя» + следствие | «может быть сложно» |
| Риски | влияние + митигация | «риски отсутствуют» |

Минимум для baseline: 3 цели, 3 не-цели, 5 FR, 3 NFR, 3 ограничения, 3 риска.

## 02-ARCHITECTURE.md

- Одна ASCII-схема контекста (система + соседи) — обязательна.
- Таблица компонентов с колонкой **«не должен»** — именно она предотвращает расползание.
- Раздел «владельцы истины»: для каждого состояния сказано, кто прав.
- Поток с поведением при ошибке, а не только happy path.
- ≥ 2 инварианта с ценой нарушения.

## 03-DATABASE.md

- Таблица хранилищ с колонкой «наше право» (read / read-write / нет).
- ER-схема текстом: сущности + связи + кардинальности.
- Таблица «правила записи»: операция → можно/нельзя → как → почему.
- Политика миграций: аддитивно, файлы, транзакция, бэкап.
- DDL — только в `db/schema.sql`; в доке смысл.

## 04-API.md

- Таблица плоскостей: транспорт, база, потребитель, авторизация.
- Эндпоинты: метод, путь, назначение, ответ, ошибки.
- Формат ошибки единый (код + сообщение + детали).
- Идемпотентность, пагинация, версионирование — по одному предложению каждый.
- Один рабочий пример `curl` с ожидаемым ответом.

## 05-MODULES.md

- Определение «модуля» в терминах этого проекта (папка/пакет/фича-флаг).
- Состав: id, тип, что делает, зависимости, статус.
- Контракт: точка входа + что модуль **не может**.
- Матрица совместимости: требует / конфликтует / права / нужен ли перезапуск.
- ≥ 3 анти-паттерна в формате «что происходит» → «правильно».

## 06-INTEGRATIONS.md

- Таблица систем: зачем, доступ, **где лежит секрет** (имя переменной).
- Модель памяти: одна тема — одно место (memory/skills/vault/docs или код/БД/wiki).
- Расписания: когда, что, куда пишет.
- Чек-лист новой интеграции — рабочий, не декоративный.

## 07-ROADMAP.md

- Каждый этап: срок + **критерий выхода**, который можно проверить командой.
- Задачи с артефактом и приёмкой; никаких «доработать».
- Граф зависимостей этапов.
- Бэклог с ценой и решением (взято/отложено/отклонено).
- Раздел «что делать при изменении внешней зависимости».

## project.yaml

- `description` — одно предложение, без «TODO».
- `stack` — фактические версии, не названия.
- `status` переключается `draft → active` только когда `--check` = 0.

## Vault-заметки

- Frontmatter: `tags`, `updated` (ISO), `status`.
- «Зачем заметка» — одно предложение сверху.
- Связи вики-ссылками; каждая ссылка ведёт на существующую заметку.
- Нет DDL, JSON-схем, логов, секретов.
- MOC: любая заметка достижима за 1 переход.

## Красные флаги по всему проекту

1. Числа без источника («примерно 300 роутов»).
2. Требование без приёмки.
3. Решение без цены.
4. Дублирование контракта в двух файлах (docs + vault).
5. Пустая таблица-заглушка, оставленная как «структура».
6. Секрет в примере конфига.
