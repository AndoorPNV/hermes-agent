# 05 · Модули и точки расширения

Версия: 1.0 · 2026-10-30

---

## 1. Формат модуля

Каждый модуль — папка `modules/<id>/` с манифестом `module.yaml` и артефактами.
Манифест — единственный источник истины о составе; установщик не угадывает.

```yaml
id: ui-workspace                 # kebab-case, == имя папки, == id плагина
type: ui                         # skill | plugin | ui | theme | i18n | mcp
version: 0.1.0
description: Панель состояния HermesUI (plan/changes/doctor) в десктопе
author: mrkee
license: MIT
platforms: [windows, linux, macos]

requires:
  - id: theme-hermesui
    min_version: 0.1.0
conflicts:
  - ui-project-map               # оба регистрируют навигацию → конфликт UX, не техники

capabilities: []                 # объявляем, НЕ выдаём; выдаёт пользователь

artifacts:
  - kind: desktop                # desktop | python | skill | skin | locale | mcp_json | patch | state
                                 # state — файлы состояния модуля (groups.json, policy.json)
    src: plugin.js
    dst: desktop-plugins/ui-workspace/plugin.js
  - kind: skill
    src: skill/
    dst: skills/hermesui/ui-workspace/

config:                          # записывается только через hermes config set
  plugins.enabled: ["ui-workspace"]

hooks: []                        # только для type: plugin
settings: {}                     # произвольные значения → settings в hermesui.db
```

### 1.1 Правила манифеста

| Правило | Почему |
|---|---|
| `id` == имя папки == `const ID` в `plugin.js` == элемент `plugins.enabled` | коллизия id убивает весь плагин без ошибки |
| `requires` только на существующий `id` | висячая зависимость = невозможный `plan` |
| `conflicts` — взаимные (оба модуля объявляют друг друга) | односторонний конфликт обнаруживается позже |
| `capabilities` пустой, если можно | каждая capability — согласие пользователя и лишний шаг |
| `artifacts[].dst` — относительно `$HERMES_HOME` | переносимость профилей |
| никаких абсолютных путей в манифесте | `F:\…` не существует на другой машине |

## 2. Типы модулей

### 2.1 `skill`

```
modules/skill-hermes-adapt/
├── module.yaml
└── skill/
    ├── SKILL.md
    ├── references/*.md
    ├── templates/*
    └── scripts/*
```

`SKILL.md` frontmatter (проверено на живых скиллах):

```yaml
---
name: hermes-adapt
description: "Use when adding or updating a HermesUI module. Install, validate, rollback."
version: 0.1.0
author: mrkee
license: MIT
platforms: [windows, linux]
metadata:
  hermes:
    tags: [hermes, plugins, ui, install]
---
```

Требования:
- Первые 57 символов `description` — самодостаточный триггер «Use when …».
- Тело — процедура, а не пересказ `docs/` (иначе две правды).
- Тяжёлое — в `references/`, шаблоны — в `templates/`, исполняемое — в `scripts/`.
- Скилл ссылается на этот проект по абсолютному пути (`F:\06_AI\HermesUI`) только в
  разделе «где что лежит», а не в каждом шаге.

### 2.2 `plugin` (Python, хуки + REST)

```
modules/guards/
├── module.yaml                 # type: plugin, hooks: [pre_tool_call], capabilities: [tools.override]
└── plugin/
    ├── plugin.yaml             # api: plugin_api.py  (относительно dashboard/)
    ├── __init__.py             # def register(ctx): ctx.register_hook(...)
    ├── dashboard/
    │   ├── manifest.json       # без него REST не монтируется
    │   └── plugin_api.py       # router = APIRouter()
    └── desktop/plugin.js       # опционально
```

Жизненный цикл:

```
apply → файлы в plugins/<id>/ → plugins.enabled=[…] → ПЕРЕЗАПУСК ГЕЙТВЕЯ
      → boot: discover → import → register(ctx) → mount /api/plugins/<id>
      → хуки активны ТОЛЬКО после выдачи capability
```

Обязательные проверки после установки:

| Проверка | Команда | Ожидание |
|---|---|---|
| импорт | `python -m py_compile plugins/<id>/*.py dashboard/*.py` | 0 |
| монтирование | `curl -o /dev/null -w '%{http_code}' …/api/plugins/<id>/state` | `401` = маршрут есть (гейтвей требует тикет), `404` = не смонтирован. `200` **ничего не доказывает**: локальный порт десктопа отвечает `{"result":123,"msg":"Unsupported protocols"}` на любой путь. Второе доказательство — строка `Mounted plugin API routes: /api/plugins/<id>/` в `logs/agent.log` |
| лог | `grep "Mounted plugin API routes" $HERMES_HOME/logs/agent.log` | строка с `<id>` |
| capability | `grep capability_check $HERMES_HOME/logs/agent.log` | `decision=allow` |

### 2.3 `ui` (desktop-плагин)

Один файл `plugin.js` — plain ESM, `export default { id, name, register(ctx) }`.
Загружается hot-reload из `$HERMES_HOME/desktop-plugins/<id>/plugin.js`.

Доступные `area`:

| Area | Что даёт | Обязательные поля `data` |
|---|---|---|
| `ROUTES_AREA` | страница в рабочей области | `path` |
| `SIDEBAR_NAV_AREA` | строка навигации | `path`, `label`, `codicon?` |
| `PALETTE_AREA` | команда ⌘K | `label`, `run`, `keywords?` |
| `KEYBINDS_AREA` | переназначаемое действие | `id`, `label`, `default?` |
| `'statusBar.left'` / `'statusBar.right'` | чип в статус-баре | `render` |
| `'panes'` | панель | `placement`, `dock?`, `width?`, `height?`, `title` |
| `THEMES_AREA` | тема в списке | полный `DesktopTheme` |
| `TRANSCRIPT_DIRECTIVE_AREA` | `::name{…}` в сообщении | `name`, `render` |
| `TITLEBAR_AREAS.center` | контрол в заголовке (mount-scoped) | `Contribute` |

Правила (цена ошибки — «интерфейс исчез»):

1. **Не регистрировать одновременно page и pane** для одной сущности.
2. **JSX запрещён** — только `jsx()`/`jsxs()` из `react/jsx-runtime`.
3. Импорты — только `@hermes/plugin-sdk`, `react`, `react/jsx-runtime`.
4. Цвета — только `var(--ui-*)`, `var(--theme-*)`, `var(--shadow-nous)`; hex запрещён.
5. Canvas — обязательный `ResizeObserver` + изменение `width`/`height` атрибутов.
6. Данные — `useQuery`/`useMutation` из SDK, не самодельный polling.
7. Ошибка бэкенда — видимый чип `backend unavailable [<err>]`, не молчание.
8. Кнопки-иконки — `aria-label` + `title`, иначе они «пустые» в дереве доступности.

Проверка: `node --check` на копии `.mjs`; затем ⌘K → **Reload desktop plugins**;
затем наличие своих меток в AX-дереве окна.

### 2.4 `theme` / `i18n`

Скин — YAML в `$HERMES_HOME/skins/<name>.yaml`, активируется `display.skin`
(применяется на CLI/TUI/desktop в пределах ~1 с). Точечная правка активного скина —
`hermes skin set <key> <hex>`; форкать `default` нельзя (теряется палитра и фон).

Языковой пакет — либо `locales/*.desktop.yaml` (+ регистрация в `i18n`), либо в UI-модуле:

```js
ctx.i18n.registerAppLocale('ru', { endonym: 'Русский', translations: { 'nav.chat': 'Чат' } })
```

Ключи берутся из `locales/_keys.desktop.json` (`npm run i18n:keys`); отсутствующие
падают в английский каталог, затем в сам ключ.

### 2.5 `mcp`

MCP-сервер — не файл, а запись в `config.yaml: mcp_servers`. Модуль типа `mcp`
поставляет JSON-фрагмент + инструкцию; применяется через API каталога
(`POST /api/mcp/catalog/install`) или `hermes mcp add`. Профиль-глобально, не по сессии.

### 3.1 `ui-dispatcher` — что именно он переключает

| Вкладка | Источник чтения | Ключ записи | Ограничение |
|---|---|---|---|
| Скиллы | `tools.skills_tool.find_all_skills(skip_disabled=True)` + `get_plugin_manager().list_plugin_skill_metadata()` | `skills.disabled` (`skills_config.save_disabled_skills`) | `hermes-agent` — `ESSENTIAL_SKILLS`, не отключается |
| Плагины (агент) | `plugins_cmd._discover_all_plugins` + `_plugin_status` | `plugins.enabled` / `plugins.disabled` (`dashboard_set_agent_plugin_enabled`) | ключ — `key` из discovery (`web/ddgs`, `platforms/telegram`), не имя манифеста |
| Плагины (десктоп) | `$HERMES_HOME/desktop-plugins/*/plugin.js` (regex по `export default`) | `localStorage['hermes.desktop.pluginDecisions.v2']` — пишет **страница**, приложение применяет по «Reload desktop plugins» | бэкенд не может: решение живёт в renderer |
| Инструменты | `tools_config._get_effective_configurable_toolsets` + `_get_platform_tools` | `platform_toolsets.<platform>` (`_save_platform_tools`); `stt` — `stt.enabled` | первый же toggle раскрывает композит `hermes-cli` в явный список — это поведение ядра |
| MCP | `mcp_servers` + `server_configs_with_sources` | `mcp_servers.<name>.enabled` | сервер, поставленный плагином, переключается только вместе с плагином (409-семантика) |

Группы (`groups.json` рядом с бэкендом, `$HERMES_HOME/plugins/ui-dispatcher/groups.json`):
`{id, kind: skill|plugin, name, note, order, items[]}`. Группа — это **выборка**, не политика:
одна позиция может лежать в нескольких группах, применение группы = «включить все члены» или
«выключить все члены». Назначение группы проекту/сессии — реализовано в политике
`project-map-ui`: `policy.json` получил поле `groups[]` (id групп, не развёрнутые имена),
бэкенд политики читает `groups.json` диспетчера на каждом вызове через `stat`-кэш и
объединяет членов выбранных групп с полем `skills`. Правка группы в диспетчере поэтому
сразу меняет все карточки, которые её выбрали; политикой управляют только группы
`kind: skill` (у политики нет оси «плагины»). Удалённая группа, на которую ссылается
политика, не разворачивается: карточка остаётся с явным списком `skills`, а диалог
показывает предупреждение «группа не найдена».

## 3.2 `project-map-ui` — статусы карточек, новая сессия, временные сессии

### Реестр для политики: только установленное

`GET /state` отдаёт реестр из живых источников ядра, а не из таблицы в коде: `skills` —
`skills_list()` (62 записи), `toolsets` — `get_all_toolsets()` (60), `mcp` — `mcp_servers`
конфига, `groups` — `groups.json` диспетчера. Плюс два поля, которых не хватало:

| Поле | Что даёт |
|---|---|
| `skills_meta[name].source` | `external` (наш `hermesui/skills`, метка «наш» в списке) / `local` (`$HERMES_HOME/skills`) / `builtin` |
| `audit.projects[pid]` | что выбрано в политике, но больше не установлено — по осям `skills`/`toolsets`/`mcp`/`groups` |
| `audit.groups[gid]` | члены группы, которых нет в установленных скиллах |
| `audit.orphan_projects[]` | записи политики для проектов, удалённых из `projects.db` |

Почему это не косметика: список выбора строился из установленного, поэтому сохранённое имя,
которого там нет, **исчезало из диалога**, оставаясь в `policy.json`. Ограничение висело на
скилле, которого не существует, а человек видел «4 скилла» и считал доступ закрытым. Теперь
диалог печатает красную строку «не установлено: …» с кнопкой «убрать», счётчик показывает
`2 / 62 · 1 нет в наборе`, на карточке проекта появляется red-метрика «нет в наборе», а записи
для удалённых проектов видны чипом в шапке карты и удаляются одним кликом (`POST /policy`
с `policy: null`). Реестр при этом остаётся честным: `ghost-skill` в список выбора не попадает.

Живой статус берётся только из RPC `session.active_list` (`LiveSessionStatus`:
`idle | starting | waiting | working | streaming | resuming`), поллинг 6 с; всё остальное
достраивается по строке `sessions` в `state.db` (`saved` — маркер «сохранить сессию» в
последнем ответе ассистента, `message_count`, `ended_at`).

| Состояние | Условие (`sessionState()` в `plugin.js`) | Вид карточки |
|---|---|---|
| `working` | живой статус из `LIVE_BUSY` (ход в полёте) | зелёный, пульсирующая точка |
| `open` | живой `idle` | синий |
| `done` | `saved` или `ended_at` | тёмно-серый |
| `idle` | есть сообщения, не живая, маркера нет | янтарный |
| `empty` | `message_count = 0` | пунктир, полая точка |
| `temp` | id есть в `ephemeral.json` | фиолетовый, пунктирная рамка, иконка `beaker` |

`id` живой строки — runtime-id, `session_key` — stored-id; карта ключуется stored-id, поэтому
`liveMap` пишет оба. ПКМ по узлу (проект или сессия) → «Новая сессия»/«Временная»:
`session.create` (+`parent_session_id` для дочерней), затем `POST /link` — он же ставит маркер
`_branched_from`, без которого ядро не листит дочернюю строку. Если у только что созданной
сессии ещё нет строки в БД, док не открывается — она уходит в основной чат
(`host.openSession`), иначе `selected` висел бы на узле, которого нет на графе.

Временная сессия (`ephemeral.py`, store `plugins/project-map-ui/ephemeral.json`):

| Роут | Что делает |
|---|---|
| `POST /ephemeral` | `{session_id, parent, cwd, project_id, boot}` → запись со штампом текущего инстанса приложения |
| `POST /ephemeral/boot` | `{boot}` → `{stale: [id…]}` — сессии, оставшиеся от закрытого приложения |
| `POST /ephemeral/drop` | убрать запись после удаления сессии |
| `GET /state` | добавилось поле `ephemeral` (тот же store) |

Удаление делает **фронтенд** каноническими RPC: `session.close` → `session.delete`
(без `close` гейтвей отвечает `4023 cannot delete an active session`). Штамп `boot` — лизинг
в `localStorage` (`project-map-ui:boot-lease`, 15 с обновление, 60 с срок): второе окно карты
присоединяется к тому же инстансу и не подметает сессии соседнего. Sweep запускается в
`register()` — на старте приложения, не на открытии страницы. Цена и альтернативы —
ADR-010: между закрытием приложения и следующим запуском строка физически лежит в
`state.db`, а в обычном сайдбаре ядра временная сессия неотличима от обычной.

### Обучающий тур по странице

Первый заход на карту показывает 7 шагов поверх страницы: кнопка «Карта проекта» в сайдбаре →
панель проектов → граф → шапка → док чата → вложенность перетаскиванием → меню по ПКМ.
Оверлей `position: fixed; pointer-events: none` — кликается только карточка, полотно под ним
живое. Факт прохода — `localStorage['project-map-ui:tour:v1'] = 'done'`; повтор — «?» в шапке
или команда палитры «Карта проекта: обучающий тур» (переходит на страницу и шлёт window-событие
`project-map-ui:tour-start`). Якоря — `data-tour`: `sidebar-nav-project-map-ui:nav` у кнопки
оболочки (id контрибуции получает префикс плагина, поэтому в резерве вариант без префикса и
поиск по подписи) и наши `pm-rail` / `pm-graph` / `pm-header` / `pm-dock`. Шаг без якоря
(док закрыт) рисуется по центру, а не ломает тур. Клавиши: `→` вперёд, `←` назад, `Esc` — пропустить.

## 3.3 `sessions` — типы сессий, след и экспорт в vault (этап 3)

Инструмент, не модуль: файлы в `$HERMES_HOME` не кладёт, живёт в `tools/sessions.py` и
вызывается CLI, cron и плагином. Источник типов — `hermesui.db:session_registry` (миграции
`0004`/`0005`), оперативный кэш — `plugins/project-map-ui/ephemeral.json`.

| Команда | Что делает |
|---|---|
| `--register <id> --kind project\|temp [--boot B]` | учёт сессии; повторный вызов обновляет запись |
| `--list [--kind …]` | реестр: тип, `live/purged`, заголовок |
| `--check` | сводка: сколько project/temp, что ждёт sweep, долги (`v_temp_trace_gaps`), project-записи без строки в `state.db` |
| `--purge [--boot B] [--dry-run]` | sweep: удаляет временные **чужого** инстанса через `hermes sessions delete`, затем проверяет след |
| `--trace <id>` | след сессии: строка `state.db`, сообщения, файл экспорта, заметки vault |
| `--export <id> [--title …] [--dry-run]` | project → заметка в `sessions/` + строка в MOC; временную экспортировать нельзя |

Контракты, которые проверены живьём:

- **«Временная не оставляет следа» доказывается, а не предполагается.** После удаления
  проверяются четыре вещи: строка в `state.db`, `messages`, файл экспорта, упоминания id в
  vault. Итог — в `purge_evidence`; несошедшееся остаётся долгом в `v_temp_trace_gaps`.
  Живой прогон: сессия создана `hermes chat --oneshot`, удалена `--purge` → `sessions 0,
  messages 0`, заметок нет, `clean: true`.
- **Экспорт делает ядро.** `hermes sessions export --format md` кладёт markdown в **каталог**
  (`<session>-session.md` + `manifest.jsonl`), поэтому обёртка работает во временном каталоге.
  Верхний YAML ядра срезается и переносится в наш frontmatter (`tags/updated/status`, `session`,
  `project`, `model`, `messages`), повторный `# Заголовок` убирается, добавляется строка
  «Связи: [[00 HermesUI (MOC)]] · [[Модули]]» — иначе `vault_check` ругается «без wiki-ссылок».
- **Индекс идемпотентен.** Строка в MOC под `## Сессии (экспорт)` появляется один раз; повторный
  экспорт той же заметки в индекс не дублируется (`indexed: false`).
- **Плагин учитывает типы сам.** `POST /ephemeral` пишет `temp.register` (с `boot`), `POST
  /ephemeral/drop` — `temp.purge` с проверкой следа. Оба вызова fail-open: репозитория рядом
  может не быть, и тогда учёт просто не ведётся, а карта работает.

Дневной `maintenance` печатает строку `сессии: project N (экспорт M), temp живых K, удалено L`
и долги, если они есть.

## 3.6 Тема, контраст и движение (этап 6)

Карта проектов раньше рисовала собственные светлые цвета (`#f2f3f5`/`#12161c`) и не замечала
тему приложения: в тёмном режиме это была светлая вставка. Теперь:

| Что | Как |
|---|---|
| поверхности и текст | токены оболочки `var(--background)`, `var(--card)`, `var(--foreground)`, `var(--muted-foreground)`, `var(--border)`; рядом наши светлые значения как fallback для SSR-проб и отдельного окна |
| цвета состояний | переменные `--pm-<state>-ink/tint/line/dot` в `STATUS_CSS`: светлый набор в `.pm-root`, светлые подписи на тёмных подложках в `:root.dark .pm-root` |
| переключение темы | без перезапуска: приложение меняет класс на `<html>`, карта перекрашивается вместе с ним (ядро синхронизирует скин через `skin.changed`) |
| анимации | `prefers-reduced-motion: reduce` гасит пульс статуса и переходы; второй путь — пункт ⌘K «Карта проекта: анимации вкл/выкл» (класс `.pm-no-motion`, живёт в `localStorage`) |

Контраст проверяется инструментом, а не глазом: `python tools/contrast.py` считает WCAG-коэффициенты
по 54 парам — скин (тёмный и `light_colors`) и цвета карты в обеих темах. Пороги: 4.5 для текста,
3.0 для крупного, «декор» (разделители, границы) проверяется глазами и в провалы не идёт.
Текущий результат: **все 54 пары проходят, худший коэффициент 4.64**; до правки было 12 провалов
(например, `faint #98a1ad` на белом — 2.61).

Что поправлено в палитре по итогам расчёта: `faint` карты заменён на `color-mix` от
`--foreground` (в обеих темах ≥4.5), `status_bar_dim` в `light_colors` затемнён
`#6E8A80 → #587267` (было 3.46), «текст на выборе» проверяется вместо «выбор vs фон» (это была
пара фона с фоном — число ничего не значило).

Осознанно **не** делалось: анимация появления карты. Пульс статуса означает «здесь идёт работа»,
то есть несёт смысл; появление узлов — украшение, а на 7 проектах любое движение только мешает.
«Единые диалоги» сведены к общим стилям (радиус, панель, шапка), но не к одному компоненту:
диалоги политики и структуры живут в разных ветках файла, и объединение — рефакторинг на 400
строк без проверяемого результата.

## 3.5 Подготовка структуры проекта (этап 5)

`tools/project_scaffold.py` — вызывается мастером создания проекта (REST `/scaffold` в
`project-map-ui`) и скиллом `project-start`. Отдельной кнопки в карточке нет (убрана 2026-11-10:
мастер и так строит каркас, а кнопка дублировала его и путала — «собрать установщик этого проекта»).

Скилл `project-start` создаёт каркас с маркерами `TODO(section)` — «дозаполни фактом». Для
кнопки это неверно: человек нажал «создать» и ждёт готовую структуру. Поэтому инструмент
вызывает тот же скрипт скилла (шаблоны не дублируются), а затем **вычищает незаполненное**:

| Что вычищается | Почему |
|---|---|
| `<!-- TODO(…) -->` | комментарий-обещание без содержания |
| строки таблиц/списков с `TODO(…)` | чинить половину строки = выдумать факт |
| заголовок с `TODO(…)` + его тело | раздел без содержания |
| ```-блок с `TODO` | схема с дырками вместо компонентов |
| пустая таблица (только шапка и разделитель) | та же заглушка, только молчаливая |
| строка «Не-цели (…):» без пунктов | анонс списка без списка |
| пустые разделы (заголовок → заголовок) | |
| ссылки на документы, которых профиль не создал | иначе битые ссылки |

После чистки: разделы перенумеровываются (иначе `## 3` и `## 6` подряд читаются как потеря),
`status:` в frontmatter становится `draft`, а документ, где содержания не осталось, **не
создаётся вовсе** — в `scaffold_manifest.json` записано, что удалено и почему.

Профили (маппинг на флаги скилла): `minimal` = `--no-db --no-api`, `standard` = без флагов,
`full` = `--modules`. Хранение: `sqlite` (локальная схема), `hermesui` (общий журнал),
`files` (JSON/Markdown), `none` (раздела данных нет).

Проверка `--check` / `GET /scaffold/check`: ни маркеров `TODO`, ни `<плейсхолдеров>` в прозе
(внутри `code` и ```-блоков они законны — это примеры синтаксиса), ни битых ссылок; манифест
читается. Отказ (`--decline` / кнопка «не надо») ничего не создаёт и пишет `project.scaffold.declined`
в аудит — пустой проект после отказа это решение, а не сбой.

Проверено на трёх профилях: `standard` — 12 файлов, `minimal` — 9, `full` — 13; в каждом
`проверка: ok`. Повторный прогон файлы не перезаписывает (содержимое по md5 не изменилось).

### Границы (после инцидента 2026-11-10)

`render()` чистил `root.rglob("*.md")` — то есть любой markdown в дереве. Запуск на каталоге, где
лежит vault, вырезал строки из заметок и удалял «пустые» документы. Теперь:

| Правило | Как реализовано |
|---|---|
| чистим только **свои** файлы | `render(root, owned=…)`, `owned` — пути из вывода скрипта (`[write]`/`[skip]`); чужой `.md` не открывается даже на запись |
| не работаем в чужом каталоге | `_refuse_foreign()`: `Obsidian`, `.obsidian`, `_archive*`, `.git`, `src`, `apps` в корне или > 60 markdown → отказ; обход только `adopt=True` |
| отказ виден сразу | текст отказа перечисляет найденные признаки, а не «не удалось» |

Проверено стендом (3 кейса + живой vault): заметка с `[...](docs/02-ARCHITECTURE.md)` остаётся
байт-в-байт (sha256 совпадает) и не попадает в `cleaned`; `F:\06_AI\HermesUI` получает отказ,
корень не меняется.

## 3.4 `save-loop` — сохранение контекста (этап 7)

Две половины одного id: `plugins/save-loop/` (REST) и `desktop-plugins/save-loop/plugin.js`
(поверхности интерфейса). Логика — `tools/save_loop.py`, тот же код у CLI, REST и кнопок.

| Команда CLI | Что делает |
|---|---|
| `--save [--session ID] [--title …] [--dry-run]` | собрать заметку и записать в vault |
| `--verify` | пересчитать хэш, сверить с журналом и frontmatter, проверить строку в MOC |
| `--last` | что прочитает новая сессия (MOC, сохранения, открытые задачи) |
| `--status` | журнал прогонов и прерванные |

Что попадает в заметку (всё выведено из данных, не из фантазии): последние 6 сообщений
пользователя и 3 ответа ассистента, число инструментальных вызовов, открытые задачи kanban,
git-ветка и изменённые файлы рабочего каталога, последние 5 коммитов, проект по cwd.

Гарантии:

- **идемпотентность** — заметка ищется по тегу `hermesui/session-save` + `session: <id>`;
  повтор обновляет её, а не создаёт вторую (заметку-экспорт `hermesui/session` не трогает);
- **атомарность** — запись в `<note>.tmp` рядом и `os.replace`; при сбое `.tmp` убирается, старая
  заметка цела (проверено: цель только для чтения → `PermissionError`, файл не изменился,
  `save_runs.status='failed'`);
- **проверка чтением** — после записи файл перечитывается, хэш сравнивается с посчитанным;
  `--verify` дополнительно проверяет, что заметка проиндексирована в MOC и является самой свежей
  (иначе новая сессия прочитает старое);
- **прерванное сохранение видно** — `v_save_interrupted` (`running` без `finished_at`),
  а не «наверное, не было».

### Где живёт кнопка (важно)

Области `composer toolbar` и `message action` в контракте плагинов **нет** — кнопку внутрь поля
ввода вставить нельзя ни нам, ни ядру (это была бы правка ядра, то есть отдельный патч-модуль по

**1 956 байт ≈ 450 токенов**, собирается из источников скриптом `tools/state_note.py`.

## 3.2 `patch-desktop-create-options` — единственная правка чужого дерева

**Не требуется с 2026-11-07.** Плагин создаёт сессию пустой (`session.create` без опций) и
пишет родителя через `POST /link` + маркер `_branched_from`; единственное место с
`parent_session_id` — автономный `link-sessions.py`, который пишет в `state.db` напрямую.
Патч оставлен в репозитории как «если понадобится снова», но после `hermes update` пересобирать
десктоп больше не нужно. История решения — ADR-011.

| Что | Где |
|---|---|
| Патч | `modules/patch-desktop-create-options/fix-canonical-create-options.patch` |
| Цель | `hermes-agent/apps/desktop/src/api/canonical-protocol.ts` (+ `.test.ts`) |
| Применение | `cd hermes-agent && git apply --3way <patch>` → `cd apps/desktop && npm run build` → заменить `release/win-unpacked/resources/app.asar.unpacked/dist` |
| Проверка | `vitest run src/api/canonical-protocol.test.ts src/api/canonical-create-options.test.ts`, `tsc -p tsconfig.json --noEmit` |
| Решение | ADR-011 |

Причина: `session.create` в гейтвее принимает `parent_session_id`, `messages` и
`idempotency_key` (`tui_gateway/contracts/sessions.py`), но canonical-клиент десктопа
фильтровал их по белому списку и падал на форке несохранённой сессии с
`Canonical gateway does not support explicit session options: parent_session_id`. Патч
расширяет белый список и добавляет тест. **`hermes update` его затирает** — после каждого
обновления патч применяется заново и renderer пересобирается; пока это не сделано, форк
черновика снова падает.

## 3.8 Владение файлами между сессиями (2026-11-10)

Несколько сессий работают в одном репозитории — и затирают друг друга: мои `probe-ws.mjs`
исчезали, потому что другая сессия переписала каталог стендов; правки `plugin.js` накладывались
одна на другую; `git add -A` уносил в коммит чужие файлы.

Механизм (`session-locks`) — координата, не блокировка файловой системы:

| Что | Как |
|---|---|
| заявка | `session_claims(path, session_id, note, claimed_at, heartbeat_at, released_at)` в `hermesui.db` (миграция `0007`) |
| кто владелец | тот, чей `heartbeat_at` свежее TTL (45 мин); брошенная заявка никого не держит |
| проверка | `pre_tool_call`: перед `write_file`/`patch` ищет чужую живую заявку |
| продление | `post_tool_call`: heartbeat себе + заявка на записанный файл |
| отказ | не «ошибка сессии», а текст: кто держит, сколько минут назад, три варианта и готовая команда `--steal` |
| аудит | `audit_log`: `lock.conflict` с `result=ok` и `lock.steal` — конфликт обработан, а не провален |
| CLI | `python tools/session_locks.py --list / --who PATH / --claim / --steal / --release` |
| видно в | `STATE.md` — блок «Держат файлы» (только живые заявки) |

Ловушка, которую поймали на тесте: `datetime('now')` в SQLite — **UTC**, а окно TTL считалось
локальным временем. Разница в 3 часа превращала живую заявку в брошенную, и блокировка не
срабатывала. Теперь окно и «минут назад» считает сам SQLite (`datetime('now', '-45 minutes')`,
`julianday('now') - julianday(heartbeat_at)`), часовой пояс машины ни при чём.

Проверено (8 пунктов, стенд `cache/scratch/test_locks.py`): A берёт файл → B заблокирован с
командой `--steal` → A пишет свой файл свободно → B забирает владение → A блокируется →
брошенная заявка (90 мин) не блокирует → в аудите `lock.conflict`/`lock.steal` с `result=ok`.

Требует выдачи `tools.override` (как `guards`): без неё хост не применит `action: block`, и
плагин остаётся наблюдателем.

## 3.7 Установщик для другого пользователя (этап 9, частично)

`hermesui build-setup` собирает **один файл** `dist/hermesui-setup-<коммит>.exe` (8 МБ), который
на чужой машине ставит весь наш слой в уже установленный Hermes. Приложение Hermes внутрь не
входит — это отдельная Electron-сборка upstream; установщик ставит наши скиллы, плагины,
модули, базу, скин и cron.

| Шаг сборки | Что делает |
|---|---|
| staging | копия слоя (135 файлов, 1,2 МБ) + `payload-manifest.json` со sha256 каждого файла |
| venv сборки | `%LOCALAPPDATA%\hermes\cache\build\pyi-venv`, PyInstaller ставится один раз |
| PyInstaller | `--onefile --console --add-data <stage>;hermesui` |
| результат | `dist/hermesui-setup-<версия>.exe` + размер и sha256 в консоли |

Что делает сам exe (`tools/setup_main.py`):

1. находит Hermes (`--home`, `$HERMES_HOME`, `%LOCALAPPDATA%\hermes`) и **отказывается** ставить,
   если `config.yaml` там нет;
2. раскладывает слой в `<home>\hermesui` (по умолчанию), прежнюю версию — в
   `.hermesui-backup/setup-<ts>/`; пишет `payload-manifest.json`;
3. `scripts/link.py apply` → external_dirs + junction'ы;
4. `hermesui apply --yes --init-db` → модули, конфиг через `hermes config set`, скин;
5. `hermesui doctor` → отчёт; код возврата 0 только если все шаги зелёные.

Ключи: `--dry-run` (план), `--yes` (без вопросов; без него в non-TTY — отказ), `--target`,
`--no-wire` (только разложить файлы), `--json`, `--verbose`.

Из UI: **страница `/hermesui`** (пункт «HermesUI» с гаечным ключом в левом меню) → кнопка
**«собрать exe»** в шапке страницы и карточка **«Установщик»** с состоянием, путём, размером,
sha256 и хвостом лога. REST живёт в плагине `ui-workspace`: `POST /build/setup` (нужен
`confirm: true`, иначе 400) и `GET /build/setup` (`idle|running|ok|failed`).

Параметр профиля называется `scaffold_profile`, а не `profile`: `profile` в гейтвее служебный
(выбор профиля Hermes, см. `hermes_cli/web_server_plugin_profiles.py`), и запрос
`?profile=standard` уходил в несуществующий профиль `standard` — в диалоге это выглядело как
красное «profile 'standard' does not exist». Старое имя поля принимается для совместимости.

Почему здесь, а не в карточке проекта: установщик не про конкретный проект — он собирает весь
слой. В карточке проекта кнопка была ошибкой размещения и убрана.

Проверено 2026-11-10: exe собран (8,2 МБ), `--dry-run` видит 135 файлов внутри, раскладка в
чистый каталог даёт 0 расхождений по манифесту, CLI из установленной копии отвечает
`изменений нет`, `doctor` работает; REST-ветка прогнана напрямую (`build_start` →
`state: ok`), диалог — тремя статическими рендерами (готово / идёт / отказ).

Не проверено и не может быть проверено мной: установка на машине без Hermes и без Python —
первый шаг честно отказывает, но живой прогон на чужой машине ещё нужен.
